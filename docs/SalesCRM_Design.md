# Sales CRM (Okasha Smart) — Design Document

**Status: APPROVED — Phase 1 in progress (Catalogue + Agents + Scope). Local-only.**
Scope: Power Highway group, Okasha Smart company.

> **Decisions locked (user, 2026-10-08):** (1) money = whole-rupee `Int`; `discount Int` on both
> quotation/order **lines and headers**. (2) Agents map to **existing** Employee+User by name — never
> create users; the dry-run lists matches + gaps for the user to resolve. (3) `close`/ambiguous stage
> resolved from the **Outcome** column (Won→WON, Lost→LOST, else flag for review — never assumed).
> (4) Dummy rows skipped but **every skipped row listed in the dry-run with its reason**. (5) One
> `quotationNo`; versions `v1,v2` (e.g. `Q-0012 v2`); **only one version may be SENT/ACCEPTED at a
> time**. (6) `crm.catalogue.cost.*` gates cost **and margin** columns in every report and export.
> (7) **Agent scope (own/team/all) is NOT deferred** — built + tested in Phase 1 for leads,
> quotations and orders, including reports and exports. (8) `company` **and** `outlet` are columns on
> Lead and SalesOrder and are filterable in every report.

This document follows the existing backend conventions (Prisma `$extends` models with `gp*`
methods, `Routes` classes mounted by `RoutesHelper.generateRoutePath`, the
`{success,message,data,statusCode}` envelope, soft-delete via `isDeleted`, `createdBy/updatedBy`
userIds, the `AppError(status,message)` → `handleError` 409 pattern) and the RBAC enforcement built
in Phase 3 (`requirePermission` + `src/middleware/rbac/featureMap.json`, generated by
`qa/featuremap2.ts`). **Every new CRM route below is specified with its featureMap access kind and
feature, and §9 lists the exact `featuremap2.ts` changes so the harness passes under
`RBAC_ENFORCE=on`.**

## 1. Goals & principles

1. **A real sales pipeline**, not a spreadsheet dump. Documents (Lead, Quotation, SalesOrder,
   Return) move through **server-enforced state machines** — illegal transitions are rejected with
   `409`, and Lost/Cancelled/Returned require a reason.
2. **Catalogue is first-class and separate from gate-pass `Item`.** Category → Brand → Product →
   (variants, price list, bundles). The gate-pass `Item` (warehouse stock) stays untouched; §4.3
   defines the single link column that connects a catalogue Product to a stock Item later, without
   coupling the two now.
3. **Computed fields are never stored.** Follow-up status, days-since-contact, probability, weighted
   value, and margin are derived at read time from the record + stage settings. (The source CSV
   *does* carry `Probability %`, `Weighted Pipeline`, `Days Since Last Contact`, `Follow-up Status`
   columns — we **drop** those on import and compute them, so they can never drift.)
4. **One timeline per record.** User-logged `LeadActivity` entries (call / WhatsApp / visit /
   quotation-sent, with outcome + next follow-up) are merged with system `ActivityLog` audit rows
   into a single chronological timeline.
5. **Agent-scoped visibility.** A `SalesAgent` sees `own` / `team` / `all` records according to
   scoped features; the row filter is enforced in the service layer (the featureMap only checks that
   the caller holds *some* read feature — same split the codebase already uses for unit-scoping).
6. **Reports are filterable and exportable** (Excel + PDF), reusing the Visitor module's export
   approach (`exceljs` buffer download; PDF via the existing gate-pass PDF path).

## 4. Schema

Prisma-style; every model carries the standard audit/soft-delete columns
(`createdAt, updatedAt, isDeleted, createdBy, updatedBy`) — omitted below for brevity except where
noted. All money is stored in **minor units is NOT used**; we follow the existing codebase which uses
`Float`/`Int` PKR — amounts are `Int` (whole rupees, matching `Item.unitPrice`/`purchaseAmount`).
`legacyId String? @unique` appears on every record that can be imported, so re-imports are
idempotent and traceable to the source row.

### 4.2 SalesAgent

```prisma
model SalesAgent {
  id            String      @id @default(uuid())

  employeeId    String      @unique                // FK -> Employee (the human)
  employee      Employee    @relation(fields: [employeeId], references: [id])
```

`employeeId`/`userId` reuse the existing Employee↔User link (Employee create auto-creates a User;
`User.employeeId` is the join). An agent's `scope` drives row filtering in every list/report service.

### 4.3 Catalogue ↔ inventory link (how it connects later, decoupled now)

The gate-pass `Item` table is warehouse stock with `quantity`, decremented in `gpApprovePass`. CRM
must not fork or duplicate it. The **only** coupling is `Product.stockItemId String?` (nullable, no
FK constraint enforced in app logic beyond a soft lookup):

- Today: `stockItemId` is left null. Catalogue and stock live independently; CRM documents reference
  **catalogue** products, not stock items.
- Later (separate approved phase): when a Product is mapped to a stock Item, `SalesOrder` confirm/
  dispatch can decrement `Item.quantity` using the **exact same logic** as `gpApprovePass`
  (load item → check sufficient qty → `AppError(409)` on shortfall → `item.update`). A
  `StockMovement` ledger can be added then. **No inventory mutation ships in the CRM phases below** —
  the hook point is documented, not wired, so approving this design does not touch gate-pass stock.

## 5. Computed fields (never stored)

Implemented in `shared/computed.ts`, applied in the read/`gpFindById`/list serializers:

| Field | Applies to | Formula |
|---|---|---|
| `daysSinceContact` | Lead | `floor((now - lastContactAt)/day)`; null if never contacted |
| `followUpStatus` | Lead | `OVERDUE` if `nextFollowUpAt < today`; `DUE_TODAY` if ==; `UPCOMING` if >; `NONE` if null |
| `probability` | Lead | from a **StageProbability settings map** (stage → %), overridable per lead only via stage change; default map: NEW 10, CONTACTED 25, QUALIFIED 40, QUOTATION 60, NEGOTIATION 75, WON 100, LOST 0, ON_HOLD 20 |
| `weightedValue` | Lead | `estimatedValue * probability/100` |
| `margin` | Quotation/Order line & totals | `sum(lineTotal) - sum(quantity*unitCost)`; `marginPct = margin/total` |
| `leadAgeDays` | Lead | `floor((now - dateReceived)/day)` |
| `isRepeatCustomer` | Lead/Order | phone seen on a prior WON lead or DELIVERED order (digits-only match, like Visitor `gpPersonHistory`) |

The stage→probability map lives in `SystemConfig` (the existing single JSONB `default` row) under a
`crm` key, so it is tunable without a deploy and `probability` recomputes everywhere at once.

## 6. State machines (server-enforced)

`shared/stateMachine.ts` holds an **allowed-transitions table** per document and a single
`transition(entity, from, to, { reason })` guard used by every status endpoint. The guard:
1. loads the current row (never trusts a client-supplied "from");
2. if `to` not in `ALLOWED[entity][from]` → `throw new AppError(409, "Invalid transition FROM→TO")`;
3. if `to` ∈ `REASON_REQUIRED[entity]` and no reason → `throw new AppError(400, "reason required")`;
4. writes the new status + `statusReason`, appends an `ActivityLog` row (§7).

This mirrors `gpApprovePass` (load → guard `status !== PENDING` → `AppError(409)` → update), promoted
to a table so every CRM document uses one code path.

**Lead** (reason required: `LOST`, `ON_HOLD`)

| From | Allowed → |
|---|---|
| DRAFT | NEW |
| NEW | CONTACTED, LOST, ON_HOLD |
| CONTACTED | QUALIFIED, LOST, ON_HOLD |
| QUALIFIED | QUOTATION, LOST, ON_HOLD |
| QUOTATION | NEGOTIATION, WON, LOST, ON_HOLD |
| NEGOTIATION | WON, LOST, ON_HOLD |
| ON_HOLD | CONTACTED, QUALIFIED, LOST |
| WON | *(terminal — may spawn Quotation/Order, §6.1)* |
| LOST | *(terminal)* |

**Quotation** (reason required: `REJECTED`)

| From | Allowed → |
|---|---|
| DRAFT | SENT |
| SENT | ACCEPTED, REJECTED, EXPIRED |
| ACCEPTED | *(terminal — may spawn SalesOrder)* |
| REJECTED | *(terminal; supersede = new version row)* |
| EXPIRED | SENT *(re-send as new version)* |

**SalesOrder** (reason required: `CANCELLED`, `RETURNED`)

| From | Allowed → |
|---|---|
| DRAFT | CONFIRMED, CANCELLED |
| CONFIRMED | PACKED, CANCELLED |
| PACKED | DISPATCHED, CANCELLED |
| DISPATCHED | DELIVERED, RETURNED, *(Reattempt: stays DISPATCHED, `reattemptCount++`)* |
| DELIVERED | RETURNED |
| RETURNED | *(terminal — spawns/links SalesReturn)* |
| CANCELLED | *(terminal)* |

*Reattempt* is a distinct endpoint (`POST /salesOrder/reattempt`) — not a status change; it
increments `reattemptCount` and logs an activity while the order remains `DISPATCHED`.

**Return** (reason required at creation; `DAMAGED` also requires a note)

| From | Allowed → |
|---|---|
| REPORTED | RECEIVED_BACK |
| RECEIVED_BACK | RESTOCKED, DAMAGED |
| RESTOCKED | *(terminal; restock hook → inventory, deferred §4.3)* |
| DAMAGED | *(terminal)* |

### 6.1 Conversions

- **Visitor → Lead** (`POST /lead/fromVisitor {visitorId}`): copies name/phone/company/notes, sets
  `visitorId`, stage `NEW`, channel `WALK_IN`. Guarded so one visitor maps to at most one lead
  (`Lead.visitorId @unique`).
- **Won Lead → Quotation** (`POST /quotation/fromLead {leadId}`): only when lead stage is
  `QUOTATION`/`NEGOTIATION`/`WON`; carries customer + the lead's product as a first line item.
- **Won Lead / Accepted Quotation → SalesOrder** (`POST /salesOrder/fromLead` /
  `POST /salesOrder/fromQuotation`): carries items, customer, city; order starts `DRAFT`.
- **Delivered/Returned Order → SalesReturn** (`POST /salesReturn/fromOrder {orderId, reason}`):
  requires a reason; links `orderId`.

## 7. Audit & timeline

- **System audit:** every create/update/transition/delete writes an `ActivityLog` row
  (`entityType` ∈ `Lead|Quotation|SalesOrder|SalesReturn|Product|SalesAgent`, `entityId`, `action`,
  `userId`, metadata diff) via `shared/crmAudit.ts`, reusing the existing ActivityLog model.
- **User timeline:** `LeadActivity` rows are the human-logged touches.
- **Merged timeline:** `GET /lead/timeline?id=` returns `LeadActivity` ∪ ActivityLog(entityType=Lead,
  entityId) sorted by time, each tagged `source: "activity" | "audit"`. Same pattern can back a
  Quotation/Order timeline (audit-only).

## 8. CSV import plan

Source files (in `Docs/`): `FINAL-Okasha_Sales_Dashboard (01 Lead Register).csv` (**96 real leads**),
`Okasha_Sales_Dashboard(01 Lead Register).csv` (**149 real leads**) — **both are imported**; both
start at `OS-LHR-2026-001`, so the original ID is NOT globally unique. `Reattempt List(Sheet1).csv`
(22 rows), `Returns sepstember(SEP 2026).csv` (69 rows).

**Principle:** importers are **dry-run by default** (`?dryRun=true` returns a cleaning report:
rows parsed, rows accepted, **every skipped row with its reason**, distinct unmapped values,
cross-file overlaps, and the agent name→Employee match/gap list) and only persist when
`dryRun=false`.

**Lead import — both registers, deduped:**
- Import **both** files. `sourceFile` + original ID (`legacyId`) together are unique (`@@unique([sourceFile, legacyId])`), so the colliding `OS-LHR-2026-001` IDs coexist with provenance.
- **Dedupe by normalized phone (digits-only) + `dateReceived`** across the two files. On a match, keep
  one lead, record both source rows' `(sourceFile, legacyId)`, and **list the overlap in the dry-run**.
- Rows with **no usable data** (blank/placeholder) are ignored and counted (not listed individually);
  **dummy rows** (`Notes` contains "Dummy …lead") are skipped **and listed individually** with reason.
- Idempotent re-runs: upsert on `(sourceFile, legacyId)`.

**Cleaning rules (derived from the actual data):**

- **Channel** → `SalesChannel`: the data has `Phone/phone`, `Walk-in/Walkin/walk in`,
  `WhatsApp/whatsapp/Whatsapp`, `Referral`, `Social Media`, `Offline Marketing/Other (Offline
  Marketing)`, `old customer`→`REFERRAL`, `Other`→`OTHER`. Case-insensitive, whitespace-trimmed
  mapping table; unknown → `OTHER` (and listed in the dry-run report).
- **Stage** → `LeadStage`: `New Lead`→`NEW`, `Contacted`→`CONTACTED`, `Qualified`→`QUALIFIED`,
  `Quotation/Proposal`→`QUOTATION`, `Negotiation`→`NEGOTIATION`, `Won/won`→`WON`, `Lost`→`LOST`,
  `Follow-up`→`CONTACTED`. **Ambiguous stages** (`close`, blanks, anything unmapped) are resolved
  from the **Outcome** column: `Won`→`WON`, `Lost`→`LOST`, otherwise the row is **flagged for review
  in the dry-run** and left at its best-effort stage (never assumed WON).
- **Priority** → `LeadPriority`: `High/high`→HIGH, `Medium/medium`→MEDIUM, `Low/low`→LOW.
- **City:** the `Notes` column actually holds the city/area (free text: `LHR`, `lahore`, `Lahore`,
  `DHA Phase 6`, `KRC`, `Gujranwala`, `Islamabad`, plus "Dummy Lahore lead …" test rows). Rule:
  map `LHR*`/`lahore`/`DHA*`/`Askari*`/`Bahria*`/`MM Alam`/`Firdous`/`Wapda`/`Valencia`/`Faisal Town`
  → `Lahore`; `KRC` → `Karachi`; keep `Gujranwala`/`Islamabad`/`Chakwal` as-is; store the raw string
  too. Rows whose city contains "Dummy …lead" are tagged `legacyId` + skipped unless
  `includeDummy=true`.
- **Agent:** the trailing `A` column holds the agent code (`AG001`..`AG008`); `Assigned Salesperson`
  holds the name: AG001 Usama Liaqat, AG002 Ghulam Mustafa, AG003 Hur Ali, AG004 Sadaf Raza,
  AG005 Hafiz Mubashir, AG006 Usman Arshad, AG007 Waleed Bin Saeed, AG008 Areeba Farooq.
  **Agents are mapped to EXISTING Employee+User rows by name** (several exist as `*@phw` users) —
  **no users are created**. The dry-run lists each agent's name→Employee match **and every gap**;
  the user resolves gaps manually before the authoritative lead import.
- **Estimated Value / Weighted Pipeline:** strip `PKR`, commas, spaces → integer. We import
  `estimatedValue`; we **discard** `Weighted Pipeline`, `Probability %`, `Days Since Last Contact`,
  `Follow-up Status` (all recomputed, §5).
- **Product/Service:** free-text, 79 distinct values mixing real products, job titles ("CEO",
  "Architect", "Coffee Shop, Manager"), SKU codes ("S32312"), and noise ("Scam mssges", "Out of
  stock", "want quotation"). Rule: fuzzy-match to a seeded Product (§10); on no match, store the raw
  string in `Lead.requirement` and leave `productId` null (reported in dry-run as "unmatched
  product"). **Never auto-create catalogue products from lead free-text.**
- **Reattempt List:** title/blank header rows skipped; real header at row 3 (`SR, Date, Name,
  Number, Tracking ID, Order NO`). Import as `SalesOrder` upserts by `legacyId=Order NO`, set
  `trackingNo`, `reattemptCount≥1`, status `DISPATCHED`. If the order already exists, only bump
  reattempt + tracking.
- **Returns:** header row 1 (`Sr, CN #, Customer Name, Date, Item Name, Mobile Number, No. Of items,
  Status, Detail, Vendor Name, Order Num, City, Address, Order Date`). Each row → `SalesReturn`
  (`legacyId=CN #`), `reason=Detail` (free-text, required — satisfied by the column),
  `courier=Vendor Name` ("Post Ex"), `trackingNo=CN #`, `city=City`, one `ReturnItem` from
  `Item Name` (+quantity `No. Of items`); link to `SalesOrder` by `Order Num` when present. `Status`
  "Order Cancel" → the linked order transitions toward `CANCELLED`/`RETURNED` (reason carried).

**Import endpoints** are `multipart/form-data` (multer memory storage, like Visitor `/import`), one
per source shape: `POST /lead/import`, `POST /salesOrder/importReattempt`,
`POST /salesReturn/import`, each honoring `dryRun`.

## 9. RBAC: features, featureMap, enforcement

### 9.1 Feature tree (registered in AppFeature)

Umbrella (for admin nav gating, parallels `appModules.quickMark.*`):
`appModules.crm.*`

Functional roots (each with the standard `read/create/update/delete/restore` leaves, plus the
special leaves noted). Scoped read/update leaves use the **parent rule** already in the middleware
(holding `crm.lead.*` grants every descendant):

```
crm.catalogue.*        -> read, create, update, delete, restore, import, export
crm.catalogue.cost.*   -> gates visibility of cost/margin (PriceList.cost, margin reports)
crm.agent.*            -> read, create, update, delete, restore
crm.lead.*             -> read.{own,team,all}.*, create, update, delete, restore,
                          transition, assign, import, export, timeline
crm.quotation.*        -> read.{own,team,all}.*, create, update, delete, transition, export
crm.order.*            -> read.{own,team,all}.*, create, update, delete, transition,
                          reattempt, export
crm.return.*           -> read.{own,team,all}.*, create, update, transition, import, export
crm.report.*           -> read, export
```

**Scope feature model (how it passes the middleware).** The middleware's parent rule grants only
*downward from ancestors*, so the three sibling leaves `read.own/team/all.*` cannot all satisfy one
required feature. Resolution: scoped read-routes require the **base** `crm.<entity>.read.own.*`, and
scopes are **granted cumulatively** — TEAM implies OWN, ALL implies TEAM+OWN. Every reader therefore
holds `read.own.*` (so the middleware check passes for all three scopes), and the **broadest leaf
held** drives the row filter. A broad grant (`crm.<entity>.read.*` or `crm.*`) implies `read.all.*`
via the ancestor rule → ALL.

Scope (`own/team/all`) is resolved in the service via `shared/scope.ts` →
`resolveScope(userId, entity)`: it loads the caller's `SalesAgent` (scope + team) and the read features
they hold, then returns a Prisma `where` fragment (`{}` for ALL, `{agentId: {in: teamAgentIds}}` for
TEAM, `{agentId: ownAgentId}` for OWN). **Every list, getById, report and export** for leads,
quotations and orders applies this filter (getById on an out-of-scope row → `403`/filtered). The
featureMap only requires the caller hold **some** `crm.X.read.*` (ancestor of all three), so the
middleware stays scope-agnostic; the row filter is the service's job. **Scope is a Phase-1
deliverable and is harness-tested (§13).** `crm.catalogue.cost.*` is a separate leaf: salespeople see
prices but not cost/margin — and it also strips `cost`/`margin` columns from **every report and
export** (not just the price list).

Add a `CRM` bucket to `permission.tsx` grouping the roots above, gated by `appModules.crm.*` (so a
role without the umbrella sees no CRM menu — matching the existing module-gating behavior). Buckets:

## 13. Harness tests (RBAC_ENFORCE=on)

Added to `qa/run.ts` (or a `qa/crm.ts` invoked by it). Personas: `QA_CRM_Admin` (all `crm.*`),
`QA_CRM_Lead` (team lead, scope TEAM), `QA_CRM_Agent` (scope OWN), `QA_CRM_Viewer`
(`crm.report.read.*` only), `QA_CRM_NoCost` (no `crm.catalogue.cost.*`).

1. **State transitions — valid & invalid:** for each document, every legal transition succeeds;
   every illegal one returns `409` (e.g. Lead NEW→WON, Order DRAFT→DELIVERED, Quotation DRAFT→
   ACCEPTED). Lost/Cancelled/Returned without a reason → `400`.
2. **Scope:** OWN agent sees only own leads/orders; TEAM lead sees team; ALL sees everything; an
   agent requesting another agent's lead by id is filtered out / `403` per feature.
3. **Conversions:** Visitor→Lead (one-to-one enforced), Won Lead→Quotation (blocked from a NEW lead),
   Accepted Quotation→Order, Delivered Order→Return (reason required).
4. **Cost/margin gating:** `QA_CRM_NoCost` gets prices but `cost`/`margin` fields are stripped and
   `/crmPriceList/withCost` + margin report → `403`.
5. **Reports totals:** funnel counts == lead counts by stage; pipeline sum == Σ estimatedValue of
   open leads; weighted == Σ(value*prob); returns-rate denominator == delivered orders; seeded
   fixtures make every total a known number the test asserts exactly.
6. **featureMap coverage:** assert every `/lead /quotation /salesOrder /salesReturn /crm*` route
   present in `featureMap.json` with `access:"feature"` and a registered `crm.*` feature (no
   `unmapped`, no `NO` registered) — this is the gate for `RBAC_ENFORCE=on`.
7. **Enforcement smoke:** a token with no `crm.*` feature → `403` on every CRM write; with the
   umbrella-only (`appModules.crm.*`) still `403` on functional routes (umbrella is nav-only).

Target: 0 unmapped CRM routes, 0 unregistered CRM features, all transition/scope/conversion/report
assertions green under `RBAC_ENFORCE=on`.
